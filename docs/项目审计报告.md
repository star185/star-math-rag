## 一、结论摘要

系统**功能完整、可以实际运行**：后端在 Python 3.14.5 下正常导入启动，`/api/health`、鉴权 401 拦截实测通过；向量库 322 片段 / 110 文档自洽，`meta` 与 `vectors` 行数一致。前端渲染路径的 XSS 防护（`escapeHtml` 贯穿 Markdown 渲染）做得比一般毕设项目扎实。

但存在四类必须处理的问题：

1. **安全问题**（5 项严重）：项目目录内的 `.env` 存有真实第三方密钥；三份鉴权实现中两份缺失令牌版本校验，改密后旧令牌不失效；知识库批量导入接口接受任意服务器路径；"禁止下载"权限可被原文预览接口绕过；向量库并发写入会损坏索引。
2. **稳健性问题**：向量库是全局单例且写入无锁、每次都全量重写索引文件，并发上传会导致索引与元数据不一致并可能在重启后直接启动失败。
3. **评测方法论问题**（对答辩影响最大）：README 与报告书的核心数据"hybrid hit@1 = 98%"经复现确认无误，但消融实验显示**其中 72 个百分点来自人工标题匹配加权规则**，纯 RRF 融合只有 23%；且 96/100 道测试题的题干直接包含期望文档的概念名，构成词面泄漏（lexical leakage），使三路检索的指标失去区分度。
4. **文档与实现不符**（12 处）：最典型的是论文称"签发 JWT 令牌（短期+长期刷新令牌）、过期自动续期"，实际是自实现的两段式 HMAC 令牌且无刷新机制；以及"42 项接口测试全部通过"在仓库中找不到任何脚本或留档。

问题分布：

| 等级 | 数量 | 含义 |
|---|---|---|
| P0 严重 | 5 | 交付前必须修复，涉及密钥、鉴权绕过、越权读取、数据损坏 |
| P1 重要 | 9 | 应在答辩前修复或至少有明确说明 |
| P2 一般 | 16 | 代码质量、性能、健壮性，可安排在答辩后 |
| 文档一致性 | 12 处不符 + 4 处无出处 | 见第六章，其中"JWT/刷新令牌"与"42 项接口测试"两项答辩风险最高 |

## 二、P0 严重问题

### P0-1 项目目录内 `.env` 存放真实第三方 API 密钥

`backend/.env` 中有三组可用凭据：

| 变量 | 位置 | 实际内容特征 |
|---|---|---|
| `LLM_API_KEY` | `backend/.env:11` | DeepSeek 生产密钥（`sk-87f…`，35 字符） |
| `VISION_LLM_API_KEY` | `backend/.env:26` | 阿里云百炼 DashScope 密钥（`sk-ws-…`，115 字符） |
| `MIMO_PROVIDER_KEY` | `backend/.env:2` | 网关密钥（`tp-ckf…`，51 字符） |

另有 `backend/.env.bak_20261027` 是旧版备份，同一批密钥的第二份留存。

**已确认没有泄漏到版本库**：`.gitignore` 正确忽略了 `.env` 与 `.env.*`，`git log --all -- "*env*"` 只显示 `backend/env.example`，`git ls-files` 中无 `.env`；`server.log`/`server.err`/`llm_test_out.txt` 中未检出密钥样式的字符串。这一点做得对。

**风险**：毕设需要提交源码与演示包，项目目录一旦打包分发或上传网盘，密钥即失效控制。`.env.bak_20261027` 尤其容易被忽略。

**建议**：
1. 立即轮换上述三组密钥（视为已暴露），不要只做删除。
2. 删除 `backend/.env.bak_20261027`。
3. 交付包中排除 `.env`，只保留 `env.example`（其中占位符已用 `sk-在这里…` 之类，`llm_configured()` 会正确识别为未配置，见 `llm.py:25`）。
4. 演示前把密钥改成环境变量注入或临时填写。

### P0-2 三份重复鉴权实现，其中两份缺失令牌版本校验 → 改密后旧令牌依然有效

系统声称"改密后作废旧令牌"，实现方式是用户表 `token_epoch` 自增，令牌携带 `ep` 声明。但校验只做在了主模块：

- `main.py:66-83`：读取数据库，比较 `payload["ep"]` 与 `users.token_epoch`，不一致返回 401 —— 正确。
- `exercise.py:48-66`：只验签名、过期时间和角色，**没有 epoch 比较**。
- `practice.py:35-53`：同上，**没有 epoch 比较**。

后果：用户修改密码、或管理员执行"重置密码"（`main.py:527` 会把 `token_epoch+1`）之后，攻击者手上泄露的旧令牌仍然可以完整访问 `/api/exercises/*`（上传、解题、导出习题册）与 `/api/practice/*`（出题、判分、记录、导出）。"改密即踢下线"的安全承诺在三分之二的接口上不成立。

**建议**：把鉴权收扰成单一实现（例如 `app/deps.py` 提供 `get_current_user` / `require_admin` / `require_download`），`exercise.py` 与 `practice.py` 改为从 `main` 导入或依赖注入，杜绝再次漂移。这是同一逻辑的第三份拷贝，本身就是设计缺陷（见 P2-1）。

### P0-3 `/api/kb/ingest-folder` 接受任意路径 → 服务器任意文档读取

`main.py:1074-1083`：

```python
@app.post("/api/kb/ingest-folder")
def ingest_folder(path: Optional[str] = None, user: dict = Depends(require_admin)):
    root = Path(path) if path else KB_SOURCE_DIR
    if not root.exists():
        raise HTTPException(404, f"目录不存在: {root}")
    files = [p for p in root.rglob("*") if p.suffix.lower() in {".md", ".txt", ".docx", ".pdf"}]
```

`path` 直接来自查询参数，无任何归一化或白名单校验，`rglob` 会递归遍历任意目录（`C:\Users\...`、`C:\Windows\...`、其他项目目录）。导入后文件路径写入 `documents.path`，而：

- `GET /api/docs/{id}/raw`（`main.py:774-813`）会把 md/txt 文件**全文** `read_text` 返回；
- `GET /api/docs/{id}/text`（`main.py:745-771`）返回全部分块正文。

两个接口都**只要求登录、不要求管理员**。因此一个完整链路是：管理员误用/账号被冒用触发一次批量导入 → 服务器上所有 md/txt/docx/pdf 被登记入库 → 任意普通用户即可全文下载阅读。这属于典型的任意文件读取 + 敏感信息泄露。

同文件还有一处放大：`ingest_folder` 导入时不复制文件、只登记原路径（`main.py:1105`），进一步扩大暴露面。

**建议**：`root = (KB_SOURCE_DIR / path).resolve()` 后校验 `root.is_relative_to(KB_SOURCE_DIR.resolve())`，拒绝越界；或干脆去掉 `path` 参数，只允许导入 `KB_SOURCE_DIR`。

### P0-4 "禁止下载"权限可被原文预览接口绕过

权限模型本身是清楚的：

- `require_download`（`main.py:93-96`）要求 `role == admin` 或 `can_download`，作用于 `GET /api/docs/{id}/download`（`main.py:726`）。
- 但 `GET /api/docs/{id}/text`（745）与 `GET /api/docs/{id}/raw`（775）只依赖 `get_current_user`。

`/raw` 对 md/txt 返回的就是文件全文。对设置了"不给下载"的用户，只要先调 `/api/docs` 拿到文档 id，再逐篇请求 `/raw`，就能把整个知识库以纯文本形式拿走，仅比直接下载少了一个 `.md` 后缀。docx/pdf 虽然 `/raw` 只返回提示字符串，但 `/text` 返回的解析分块已足以还原主要内容。

**建议**：明确"可读"与"可下载"的边界。若业务意图是"能看但不能导出"，则 `/raw` 应降级为分页预览或截断返回；若意图是"可读即可导出"，则应删掉 `can_download` 这套自以为是的限制，避免给人错误的安全感。

### P0-5 向量库全局单例 + 无锁 + 全量重写 → 并发下索引损坏、重启失败

`vector_store.py:450` 在模块导入时创建 `STORE = VectorStore()`，全进程共享一份内存状态。写操作：

- `add()`（223-237）：`self.vectors = np.vstack([...])`，`self.meta.append(...)`，然后 `save()`
- `delete_by_doc()`（239-251）：重建列表与矩阵切片，然后 `save()`
- `save()`（212-215）：`INDEX_PATH.write_text(...)` + `np.save(VEC_PATH, ...)`，**两个文件先后覆写，非原子**

三个具体后果：

1. **读写竞争**：`_vector_search`（302-337）用 `self.vectors @ q` 得到长度 N 的分数，再按 `self.meta[int(i)]` 取元数据。若在此期间另一线程执行了 `add`，`len(self.meta)` 与 `vectors.shape[0]` 短暂不一致，会抛 `IndexError` 或返回错位片段（A 文档的分数配上 B 文档的元数据）。
2. **文件不一致**：两个并发上传各自 `save()`，`index.json` 可能来自 A、`vectors.npy` 来自 B。下次启动 `load()`（203-210）直接 `np.load` + `json.loads`，**没有任何长度校验或异常保护**，长度不一致时会在第一次检索时崩，文件损坏时则整个应用启动即失败。
3. **导入复杂度**：`ingest_folder` 对每个文件调一次 `STORE.add()`（`main.py:1115`），每次全量重写 322 片段的向量矩阵和整份 `index.json`。导入 100 个文件的 IO 量是 O(N²)，且中途失败会留下半个索引。

本次实测当前状态是自洽的（`meta` 322 = `vectors` 322×512），说明日常单用户使用没踩到，但这是"还没踩到"而非"踩不到"。

**建议**（按性价比排序）：
1. `save()` 改为写临时文件再 `os.replace` 原子替换，`load()` 加长度一致性校验，不一致时以 DB 的 `chunks` 表为准重建。
2. `VectorStore` 全部写操作用一把 `threading.RLock` 保护（读操作可以不加，但要在同一临界区里取 meta 与 vectors 的快照）。
3. `ingest_folder` 改为收集完所有 items 后一次性 `add()`，把 N 次全量写降为 1 次。

## 三、P1 重要问题

### P1-1 文档上传无大小限制，习题上传的大小检查又在写盘之后

- `POST /api/docs/upload`（`main.py:593-607`）：`shutil.copyfileobj(file.file, f)` 直接把请求体落盘，**没有任何字节数上限**。`EXERCISE_MAX_MB` 只作用于习题模块。一个超大文件即可打满磁盘。
- `POST /api/exercises/upload`（`exercise.py:344-352`）：虽然检查了 `EXERCISE_MAX_MB`，但检查发生在 `copyfileobj` 完成**之后** —— 10 GB 文件会先完整写进磁盘，然后才被告知"文件过大"。

两处都只按扩展名判断格式（`main.py:603`、`exercise.py:342`），不校验文件头。结合 `parse_pdf` 用 pypdf 全量解析（`parsers.py:95-107`，无页数/大小上限）与 `parse_docx` 调用 pandoc 子进程（`parsers.py:67-92`），构造一个大 PDF 或恶意 docx 可以让解析阶段长时间占满 CPU 与内存。

**建议**：流式复制时累计字节数，超限立即 `break` 并删除临时文件；`UploadFile` 改用 `await file.read(65536)` 分块；PDF 增加页数上限。

### P1-2 登录无速率限制，配合单轮 SHA256 与弱默认口令

- `main.py:291-296`：密码错误仅返回 401，无失败计数、无延迟、无账号锁定、无 IP 限速。
- `security.py:15-18`：`hash_password` 是**单轮** `sha256(salt + password)`。这种构造对离线字典攻击几乎没有成本（GPU 每秒数十亿次）。
- `config.py:62`：默认口令 `admin123`；`backend/.env` 中 `DEFAULT_ADMIN_PASSWORD` 也以 `admin1` 开头（8 字符）。
- 启动时还会强制把该账号提升为 admin 并开通下载权（`main.py:220`）。

相比之下找回密码流程做得相当规范（冷却期 `main.py:343`、尝试次数上限 377、一次性码只存哈希 488、防用户名枚举 331），说明团队知道该怎么写，只是登录这条主路径没做。

**建议**：`hash_password` 换成 `hashlib.scrypt` 或 `pbkdf2_hmac(sha256, 100_000+)` 加随机 salt（Django 风格升级编码，兼容旧库时按前缀区分）；登录失败按 `username + IP` 做指数退避；首次启动强制改密（`must_change_password` 字段已经存在，直接复用）。

### P1-3 解题接口接受客户端提交的任意题目列表，且无数量上限 → LLM 费用放大

`exercise.py:393-400`：

```python
def solve(source_id: int, body: SolveIn, user: dict = Depends(current_user)):
    ...
    questions = body.questions or loads(src.get("questions_json"), [])
```

`body.questions` 优先于服务端缓存，意味着任何登录用户可以让服务器对**自己构造的任意文本**执行 RAG 检索 + LLM 生成。同时 `SolveIn.questions: list[dict] = []`（`exercise.py:313-314`）没有 `max_length`，`_solve_one` 在循环里逐题调用一次 LLM（`exercise.py:284`，单次超时 `LLM_TIMEOUT=90`）。

`SOLVE_MAX_QUESTIONS=20` 只在**识别**阶段生效（`exercise.py:205`、`235`），解题阶段完全没有约束。一个请求提交 1000 道题，就是 1000 次付费调用。同类问题还有 `POST /api/exercises/knowledge/explain`（`exercise.py:700-719`）与 `POST /api/practice/grade`（`practice.py:198-220`），都是"登录即可无限调用付费 LLM"。

**建议**：`subject` 一律以服务端缓存的 `questions_json` 为准，忽略客户端传入；给 `questions` 加 `Field(max_length=20)`；对每用户加 LLM 调用配额（DB 计数即可）。

### P1-4 CORS 通配来源与允许凭证同时开启

`main.py:49-55`：

```python
app.add_middleware(CORSMiddleware, allow_origins=["*"], allow_credentials=True, allow_methods=["*"], allow_headers=["*"])
```

`*` 与 `allow_credentials=True` 是语义冲突的组合（浏览器按规范会拒绝带凭据的通配符响应），实际效果是任意站点都能发起无凭据跨域请求。当前鉴权用 `Authorization` 头而非 Cookie，攻击者无法自动带上受害者令牌，风险被削弱；但配置本身是错的，且一旦将来改用 Cookie 会话就会立刻变成真实漏洞。

**建议**：`allow_origins` 收敛到 `["http://127.0.0.1:8000", "http://localhost:8000"]`，或干脆删掉这个中间件（同源部署不需要 CORS）。

### P1-5 异常原文回显到前端

多处把内部异常字符串直接拼进响应：

| 位置 | 泄漏内容 |
|---|---|
| `main.py:663` | `f"入库失败: {e}"` |
| `rag.py:180` | `f"生成出错: {e}"`，且该文本会作为回答写入消息表 |
| `llm.py:127` | `f"\n\n[生成失败: {e}]"` |
| `exercise.py:304` | `f"（解题失败: {e}）"` |
| `exercise.py:390` | `f"解析失败: {e}"` |
| `exercise.py:413` | SSE `{'type':'error','detail':str(e)}` |
| `exercise.py:719` | `f"（LLM 解释生成失败：{e}）"` |

`urllib` 的异常消息通常包含完整的请求 URL、上游返回的响应体片段；文件异常包含绝对路径。这些都会显示给最终用户，也方便攻击者摸清内部结构。

**建议**：面向用户统一返回"操作失败，请稍后重试 + 错误码"，详细原因写 `logging`；前端按错误码给出提示。

### P1-6 没有任何自动化测试

`requirements.txt` 未包含 pytest，仓库无 `tests/` 目录。唯一的验证手段是 `backend/scripts/smoke_test.py`（126 行，手工冒烟）与 `smoke.bat`。

对毕设项目而言，最该覆盖且成本最低的三块完全没有测试：
- 检索层：`BM25Index.score`、`LocalEmbedder.encode`、`_rrf_merge` 的排序正确性（纯函数，极易测）。
- 鉴权：令牌过期、epoch 失效、角色/下载权限的 401/403 分支（三份实现已经漂移，测试能立刻发现）。
- 分块：`split_text` 对父子块、overlap、超长段落的边界行为。

**建议**：优先补 `test_security.py`（epoch 漂移那个 bug 一个断言就能抓到）与 `test_vector_store.py`（RRF 排序 + 空索引 + 维度不匹配）。

### P1-7 判分结果由客户端提交，做题记录与错题本不可信

`practice.py:259-269`：`save` 直接使用请求体里的 `body.correct` 落库。客户端可以伪造"全对"，统计口径（`practice.py:504-508` 的今日题数、正确率）随之失真。`grade` 接口本身给出了服务端判定，但那是另一条请求，`save` 并不复用它的结果。

**建议**：`save` 只接受 `qid` 与用户答案，服务端重新判分后写入；或缓存最近一次 `grade` 结果并要求 `qid` 匹配。

### P1-8 评测记录接口无用户隔离

`main.py:1020-1031`：`eval_records` 表（`db.py:105-115`）没有 `user_id` 字段，`GET /api/eval/list` 对任何登录用户返回全部记录，包含他人提问文本与模型回答。

**建议**：表加 `user_id`，查询加 `WHERE user_id=?`；管理员视图单独开接口。

### P1-9 `/api/health` 无鉴权，暴露服务器绝对路径

实测返回：

```json
{"ok": true, "kb_source": "C:\\word\\知识库\\知识库\\数学_RAG", "vector": {...}}
```

`main.py:1055-1071`。健康检查无需登录是合理的，但 `kb_source` 暴露了服务器目录结构（用户名、盘符、业务目录命名）。同接口还回传 `llm_configured`、片段数、top_k 等内部参数，对攻击者是有用的侦察信息。

**建议**：公开 health 只返回 `{"ok": true, "version": ...}`，其余字段移到需要鉴权的 `/api/system/info`。

## 四、P2 一般问题

### P2-1 同一逻辑的多份拷贝

| 重复内容 | 位置 |
|---|---|

### P2-3 检索性能的隐性瓶颈

- **BM25 无倒排索引**：`BM25Index.score`（`vector_store.py:92-105`）对每个查询词遍历全部文档计算 tf，复杂度 O(词数 × 文档数)；`self.docs` 是把全文分词结果整份存在内存里的词表列表，322 片段尚可，数千片段后单次查询会到几十毫秒量级。
- **向量检索全量矩阵乘**：`vector_store.py:310`，每次查询 322×512 全乘一遍，可接受但无索引结构。
- **索引文件冗余**：`index.json` 里每个 chunk 都完整存一份 `parent_content`（`parsers.py:303` 写进每个子块），父块上限 1600 字符。一个父块切 5 个子块，就存了 5 份父块全文。当前 322 片段的 `index.json` 体积被放大了数倍，且每次 `save()` 全量重写。
- **`_vector_search` 每查询重建缓存**：`vector_store.py:313-324` 两层 Python 循环遍历所有 meta 做字符串拼接与 `in` 判断。

### P2-4 RapidOCR 引擎每次调用重新初始化

`parsers.py:169-173`：

```python
from rapidocr import RapidOCR
engine_ocr = RapidOCR()          # 每次调用都重新加载模型
res = engine_ocr(str(path))
```

RapidOCR 的构造包含 onnxruntime 会话创建与模型加载，通常是秒级开销。docx 含多张图片时会逐张调用（`exercise.py:143`），耗时叠加明显。

**建议**：模块级单例 + `functools.lru_cache` 或全局懒加载。

### P2-5 同一题目重复检索

`exercise.py` 的 `_solve_one` 先调 `_solve_prompt`（`248` 行内部 `retrieve`），构造完后又调一次 `retrieve` 取 `sources`（`299` 行）。同一题面检索两遍，纯浪费。

### P2-6 相似题查重是 O(n²)

`exercise.py:750-766`：先 `SELECT` 该用户全部题目（无 LIMIT），再对每条做 `difflib.SequenceMatcher`（复杂度与两条文本长度乘积相关）。用户积累几百道题后，这个同步接口会明显卡顿，并占用线程池。

### P2-7 题库每次请求全量读文件

`practice.py:56-67` 的 `_load_questions()` 每次调用都重新 `json.loads` 两个文件（`test_questions.json` 70 KB + `kmath_questions.json` 116 KB）；`_find(qid)`（70-74）又在其中线性查找。`grade`、`explain`、`export` 每次请求至少触发一次全量解析。

**建议**：模块级缓存 + 文件 mtime 失效。

### P2-8 frontmatter 解析不支持 CRLF

`parsers.py:188-193`：

```python
if not text.startswith("---"):
    return {}, text
m = re.match(r"^---\n(.*?)\n---\n?", text, re.S)
```

正则硬编码 `\n`。在 Windows 上编辑、以 CRLF 保存的 md 文件会匹配失败，`book`/`part`/`pages`/`title` 元数据全部丢失，文档退化为用文件名当标题、`part` 为空——而 `part` 为空会让按模块过滤检索（`vector_store.py:292`、`330`）失效。知识库语料若来自不同来源，这个 bug 会静默发生。

**建议**：先 `text.replace("\r\n", "\n")` 再判断，或用 `re.match(r"^---\r?\n(.*?)\r?\n---\r?\n?", ...)`。

### P2-9 LLM 流式解析收到 `[DONE]` 未退出外层循环

`llm.py:92-94`：`if payload == b"[DONE]": break` 只跳出内层 `while b"\n" in buf`，外层 `while True` 继续 `resp.read(256)` 直到连接关闭。功能上不会出错（服务端会关流），但语义不正确，也浪费了一次阻塞读。

### P2-10 启动钩子使用了已废弃 API

`main.py:194`：`@app.on_event("startup")`。FastAPI 0.109 起推荐 `lifespan`，新版会产生 DeprecationWarning，未来主版本会移除。

### P2-11 静态目录挂载可能遮住 `/api` 索引端点

`main.py:1140-1146`：`app.mount("/", StaticFiles(...))` 先注册（1141），`@app.get("/api")` 后注册（1144）。Starlette 按注册顺序匹配，先注册的 `Mount("/")` 会捕获所有未命中前面路由的请求，`GET /api` 大概率返回静态目录的 404 而不是那个 JSON。验证方式：启动后访问 `http://127.0.0.1:8000/api`。

### P2-12 前端 localStorage 解析无保护，存储损坏即白屏

`app.js:4-5` 在模块顶层执行：

```javascript
token: localStorage.getItem("rag_token") || "",
user: JSON.parse(localStorage.getItem("rag_user") || "null"),
```

`rag_user` 若被写坏（历史版本字段变更、手工修改、其他脚本污染），`JSON.parse` 抛异常会中断整个脚本求值，页面停在上一次渲染的状态、所有事件绑定不生效，用户看到的是"白屏/按钮全哑"，且没有自愈路径。

**建议**：`try { ... } catch { localStorage.removeItem("rag_user"); }` 包一层。

### P2-13 SQLite 未启用 WAL

`db.py:167-179` 的连接只设了 `foreign_keys`。默认 rollback journal 模式下，写事务会阻塞读事务，SSE 长连接期间（`main.py` 的 `event_stream` 在 `finally` 里写消息）与用户其他请求并发时容易出现 `database is locked`。`timeout=30` 只是把冲突变成 30 秒等待。

**建议**：`init_db` 里执行 `PRAGMA journal_mode=WAL`。

### P2-14 数据库迁移吞掉所有异常

`db.py:186-209` 与 `main.py:199-211`：一串 `try: ALTER TABLE ... except Exception: pass`。本意是"列已存在则忽略"，但同时也吞掉了语法错误、锁冲突、磁盘满等真实故障，结果是列没加上、服务带着不完整的表结构继续跑，直到某个查询报"no such column"。

**建议**：捕获后检查 `PRAGMA table_info` 确认列确实存在，不存在则抛出。

### P2-15 `requirements.txt` 无上界、无锁文件

`backend/requirements.txt` 全部是 `>=`（`fastapi>=0.110`、`numpy>=1.26`、`rapidocr>=3.0` 等），没有 `constraints.txt`/`uv.lock`/`pip freeze` 输出。当前环境是 Python 3.14.5（比多数库的 CI 覆盖更新），任何一次 `pip install -U` 都可能改变行为。毕设复现要求"环境可重建"，这一点目前做不到。

**建议**：交付时补一份 `requirements.lock.txt`（`pip freeze` 结果），`README` 注明实测版本。

另有小问题：`email-validator` 在依赖里，但 `users.email` 列注释明确写着"仅预留"（`db.py:199`），没有实际使用。

## 五、评测方法论专项（本次审计最重要的发现）

README 与报告书的核心数据是这张表：

| 检索模式 | hit@1 | hit@3 | hit@5 | MRR |
|---|---|---|---|---|
| 向量（vector） | 97.0% | 98.0% | 99.0% | 0.9775 |
| 关键词（keyword） | 96.0% | 98.0% | 100% | 0.9733 |
| **混合（hybrid）** | **98.0%** | **99.0%** | **100%** | **0.9858** |

审计做了三件事：复现、消融、检查测试集质量。

### 5.1 数字可以精确复现

在现有 322 片段 / 110 文档的库上，调用 `eval_retrieval.py` 完全相同的链路（`rag.retrieve`），得到 97/98/99/0.9775、96/98/100/0.9733、98/99/100/0.9858 —— 与 `storage/eval_retrieval.json` 和文档**逐位一致**，100 题的 `expected_source` 全部成功映射到文档 id。数据不是编造的，可以复现。

### 5.2 消融实验：98% 里有多少是算法，有多少是规则

`retrieve()` 在检索结果上叠加了两层人工规则：

1. **标题加权**：`_boost_title`（`vector_store.py:386-406`）与 `_bm25_search` 内联加权（`vector_store.py:267-284`），查询词命中文档标题时给 `8.0`/`10.0` 量级的加分。注意 RRF 分数本身只有 `1/(60+rank) ≈ 0.016` 量级——这些加权不是"微调"，而是**完全支配**排序。
2. **关键词过滤**：`_relevance_ok`（`rag.py:40-72`）用滑窗关键词做命中判定，不命中就丢弃。

把这两层依次关掉，重跑同一批 100 题：

| 条件 | vector hit@1 | keyword hit@1 | hybrid hit@1 |
|---|---|---|---|
| A. 现状（含全部人工规则） | 97.0% | 96.0% | **98.0%** |
| B. 关闭标题加权（保留过滤） | 16.0% | 33.0% | **26.0%** |
| C. 关闭标题加权 + 关闭关键词过滤 | 97.0% | 96.0% | **98.0%** |
| D. 纯 RRF（B+C 的组合，只留融合） | — | — | **23.0%** |

读法：

- **B 组**是"加了人工过滤、但没有标题加权"的状态：hybrid 从 98% 掉到 26%，掉了 72 个百分点。这说明论文里那 98% 的绝大部分来自"查询词出现在文档标题里就给高分"这条规则，而不是 RRF 融合。
- **C 组**反转到 97/96/98：一旦把 `_relevance_ok` 的关键词过滤也关掉，纯余弦 / 纯 BM25 又能回到 97/96%。说明 `_relevance_ok` 对纯向量检索是**有害的**——它把本来排在第一的期望文档滤掉了；只有在标题加权把期望文档顶到极高分数时，过滤才不再误伤。**两层规则互为前提，拆掉任何一层都会断崖，这是典型的脆弱系统。**
- **D 组**是无人工规则的纯 RRF：23%，**低于 B 组里单用 BM25 的 33%**。也就是说，在没有人工补丁的条件下，混合检索反而不如关键词单路——与"双路互补带来提升"的结论方向相反。

### 5.3 测试集存在词面泄漏，指标失去区分度

统计 100 道题的题干与其 `expected_source` 文件名的概念名重合情况：

```
题干直接包含期望概念名: 96/100 = 96%
样例：1「什么是对数函数？」→ 10_概念·对数函数.md
      2「什么是矩阵？」    → 10_概念·矩阵.md
      7「什么是不定积分？」→ 10_概念·不定积分.md
概念名长度中位数 4 字
```

96% 的问题把答案文档的标题原样写在了问题里。在这种题面上，字符 n-gram 哈希向量（当前实际使用的 `LocalEmbedder`，`/api/health` 显示 `embedder: "LocalEmbedder"`, `dim: 512`）、BM25、RRF **本质上都在比同一件事：字面重合度**。所以三种模式都能到 96-98%，C 组出现"关掉所有规则仍是 97/96/98"也就不奇怪了。

### 5.4 结论与修改建议

必须承认的事实：

1. 97% / 96% / 98% 三者之间只差 1-2 道题。100 题样本下 1 道题就是 1 个百分点，这个差距落在抽样噪声内，**不足以支撑"混合检索优于单路检索"的结论**。
2. 真正让指标好看的，是标题匹配加权 + 关键词过滤这套针对数学概念卡的人工规则（另见 `rag.py:91-97` 的反例意图联动、`vector_store.py:283-286` 的"标题精确命中强制置顶"）。这是合理的工程手段，但论文若把它归于"RRF 融合的贡献"，属于归因错误，答辩时很容易被追问"消融实验做过吗"。
3. 当前向量路是 512 维字符 n-gram 哈希投影，不是语义 embedding。README 写"向量语义召回"、技术栈写"向量语义 + BM25"，措辞偏强；实际是"字面 n-gram 向量"。这点应如实表述，或补充实验证明它与 BM25 的差异来源（当前数据显示二者高度相关）。

建议的补强（按性价比排序）：

1. **补一张消融表**：把 5.2 的四行数据放进论文。它比 98% 更有说服力，因为展示了"知道每个组件贡献多少"，这恰恰是审阅老师想看的工程判断力。
2. **补一个"改写题"子集**：取 30 道题，把题干里的概念名替换为同义描述或场景描述（"什么是对数函数"→"形如 log_a(x) 的函数有哪些性质，为什么要求底数大于 0 且不等于 1"），单独报告一组 hit@K。这才能真正区分向量路与关键词路。
3. **把标题加权诚实归因**：在论文里说明"针对数学概念卡标题即术语的特性，增加了标题命中加权"，并给出未加权基线（16-33%）作为对照。这比一个孤立的 98% 更能体现工作深度。
4. 措辞修正：`README.md:10`「向量语义 + BM25 关键词双路召回」→ 建议改为「字符 n-gram 向量 + BM25 双路召回」，或在配置了远程 Embedding 时再声称语义检索。

### 6.4 表述风险提示

1. **"严格评测"与"单人标注"的矛盾**：摘要与结论把 hit@K 写成对检索效果目标的达成验证，但 `README.md:113` 自己承认"测试集为单人标注，未做双人一致性校验"。论文正文没有这条限制声明，评阅时几乎必问"标注者是谁、一致性系数多少"。结合第五节发现的词面泄漏（96/100 题干含期望概念名），建议在论文里主动交代测试集的构造方式与局限，比被追问更好。
2. **"向量语义检索"**：当前实际运行的是 `LocalEmbedder`（`/api/health` 显示 `embedder: "LocalEmbedder"`, `dim: 512`），字符 n-gram 哈希投影，本质是字面匹配，不是语义表示。README 技术栈与 3.x 节的"语义"措辞需弱化，或明确写"本地字符 n-gram 向量，可切换远程 Embedding"。
3. **"逐题解题流式"**：`exercise.py:409-410` 是 `_solve_one(q)` 阻塞完成后一次性 `yield` 整题结果，SSE 粒度是"逐题"而非"逐 token"。若论文写"流式解题"，需说明粒度，避免被现场对比问答接口的逐 token 流式而质疑。
4. **代码有、文档未提的功能**：注册与邀请码、找回密码与管理员重置码、下载权限控制、`/api/practice/*` 整套、习题册知识点查询/解释、相似题查重（`POST /api/exercises/similar`）、`deploy-tunnel.bat` 内网穿透。这些是加分项，README 接口表与报告表 3.1 都缺，建议补全——工作量描述越完整，答辩时的"你做了多少"越好回答。
